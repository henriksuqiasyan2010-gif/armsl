# Правила проекта

Школьный ML-проект: распознавание 12–22 динамических жестов армянского
жестового языка в реальном времени через веб-камеру. CPU-only ноутбук,
автор — новичок в ML, весь код проходит через собеседование с автором
(объяснение построчно) перед тем, как считается принятым.

## Стек и версии — жёстко

- Python 3.9–3.12 (mediapipe официально не поддерживает 3.13+, ставок
  на будущее не делаем)
- numpy: используй версию, совместимую с установленной версией
  mediapipe (актуальные mediapipe с numpy 2.x работают)
- MediaPipe Tasks API только: mediapipe.tasks.python.vision.HandLandmarker.
  Модуль mediapipe.solutions.hands НЕ существует в актуальных версиях —
  никогда не используй его, даже как fallback или в комментариях-примерах.
- Модель детекции рук — локальный файл models/hand_landmarker.task,
  никаких скачиваний во время выполнения программы.
- GRU через tensorflow/keras для классификации, не LSTM (если не оговорено
  отдельно) — GRU легче на CPU.
- Tkinter для GUI (входит в стандартную библиотеку, отдельно не ставить).
- В src/config.py выносятся КОНТРАКТНЫЕ И МОДЕЛЬНЫЕ константы: размеры
  и раскладка векторов, длина окна, индексы точек, пороги детекции,
  пути к файлам, гиперпараметры. Никаких магических чисел (30, 60, 128,
  пороги) напрямую в других файлах.
  Константы оформления (цвета отрисовки, толщина линий, размер шрифта,
  длительность отсчёта, сглаживание FPS) в config.py НЕ выносятся —
  они живут там, где используются: в demo_tracking.py, record_session.py
  и других скриптах. Они ни на что в данных и модели не влияют, и
  тащить их в общий конфиг значит смешивать контракт с оформлением.

## Контракт данных — не менять без согласования

- Один образец жеста = np.float32 массив формы (60, 128).
  60 = число кадров в окне (~2–4 с при типичном FPS вебкамеры).
  128 = 2 руки × 21 точка × (x, y, z) [126] + 2 флага видимости руки.
- Порядок в векторе кадра фиксирован по handedness: первые 63 числа —
  левая рука, следующие 63 — правая. Если порядок нарушить —
  модель будет обучаться на шуме. Это самое частое место ошибки,
  проверяй тестом на каждую реализацию features.py.
- Метка руки от MediaPipe используется КАК ЕСТЬ, инвертировать не нужно.
  Проверено вживую (demo_tracking.py, кадр без зеркалирования): физически
  правая рука -> "Right" (confidence 0.98–0.99), левая -> "Left".
  Кадр камеры не зеркалим — ни при записи, ни в реальном времени:
  зеркалирование поменяет метки местами и сломает контракт выше.
- Если рука не найдена в кадре — соответствующие 63 числа = 0.0,
  флаг видимости = 0. Кадр не пропускается, окно всегда ровно 60 кадров.
- Файлы датасета: data/raw/{label}/{person}_{session}_{idx}.npy
- В .npy хранятся СЫРЫЕ векторы: результат frame_to_vector без
  normalize_window. Нормализация применяется при чтении, в load_dataset.
  Причина: нормализация — часть препроцессинга, а не данных. Сырые
  данные переживают смену препроцессинга, нормализованные — нет
  (нельзя ни сравнить "с нормализацией / без", ни поменять алгоритм
  нормализации, ни честно проверить окно короче, не переснимая жесты).
- Метаданные: data/meta.csv, колонки:
  file,label,person,session,date,lighting,background,distance_m,notes
- data/labels.csv — ЕДИНСТВЕННЫЙ источник истины по классам. Колонки:
  label_id,armenian,pronunciation,meaning. label_id — ASCII-транслитерация,
  именно она идёт в код и в пути к файлам; остальные поля справочные.
  Порядок строк (без заголовка) = порядок классов = индекс выхода softmax.
  Строки только дописываются в конец: переставлять и удалять нельзя —
  индексы поедут, и модель начнёт показывать не те слова. Если список
  изменился — модель переобучается.
  Отдельного models/labels.json НЕТ и заводить его не нужно: models/
  исключена из git, такой файл не пережил бы clone, а дублирование
  списка в двух местах — это и есть тот самый рассинхрон.
  Когда появится train.py: он сохраняет снимок списка классов рядом
  с весами ДЛЯ ПРОВЕРКИ (не как второй редактируемый список), а
  predictor.py при несовпадении со свежим labels.csv отказывается
  работать с понятной ошибкой, а не показывает чужие слова.

## Нормализация окна — не менять без согласования

- origin (сдвиг) и scale (масштаб) считаются ОДИН РАЗ на всё окно и
  применяются одинаково ко всем кадрам. Не пересчитывать по каждому
  кадру: если в каждом кадре сдвигать к текущему запястью, запястье во
  всех кадрах окажется в одной точке и траектория движения исчезнет —
  а динамические жесты различаются именно траекторией.
- Способ свёртки по кадрам — МЕДИАНА (не среднее и не первый валидный
  кадр). Первый кадр ничем не защищён: глитч детекции именно на нём
  испортит всё окно. Среднее утягивается выбросом (например, кадр со
  смазом при быстром движении). Медиана игнорирует пару плохих кадров.
- origin и scale — ОБЩИЕ на обе руки, а не по одному на каждую. Если
  нормализовать каждую руку относительно себя самой, обе окажутся в
  начале координат, и взаимное расположение рук будет потеряно — а
  часть жестов двуручные. Общий сдвиг+масштаб переносит и растягивает
  пару рук как одну фигуру, углы и расстояния между руками не искажая.
- Отсутствующая рука остаётся ТОЧНЫМ нулём, решает это флаг видимости,
  а не проверка "координата похожа на ноль".
- Масштаб оценивается по размеру ладони (запястье -> MCP среднего
  пальца) и защищён нижним порогом: никаких NaN/inf на выходе ни при
  каких входных данных.

## Разбиение данных — критично для честности результатов

- Никогда не используй случайный (random) train/val split.
- Разбиение — только по группам person + session: вся сессия одного
  человека целиком уходит либо в train, либо в val.
- Причина: случайный split даёт утечку данных (соседние кадры одного
  движения похожи), что даёт фальшиво высокую точность и провал в
  реальном времени. Если пишешь dataset.py — добавь тест, что
  пересечение групп train и val пусто.

## CLI-скрипты в корне проекта — не модули src/

- record_session.py и demo_tracking.py — осознанно CLI-скрипты в корне
  проекта, а не модули src/. Их содержимое (камера, обработка клавиш,
  отрисовка на экране, стейт-машина "жду/отсчёт/запись") — интерактивная
  обёртка вокруг логики, а не сама логика. Вся тестируемая логика уже
  живёт в src/ и покрыта тестами там (record_sample/load_labels в
  dataset.py, HandTracker в landmarks.py, frame_to_vector/normalize_window
  в features.py) — в самих CLI-скриптах тестировать нечего, кроме
  cv2-цикла с реальной камерой, который в CI не гоняется.
- src/recorder.py в проекте больше нет. В исходном списке файлов был
  заявлен модуль recorder.py в src/, но по факту вся его функция
  реализована как record_session.py (см. выше). Держать вдобавок вечно
  пустой src/recorder.py как "заглушку, которая никогда не наполнится"
  было бы вторым источником истины о том, где живёт запись датасета —
  а именно с такого рассинхрона (см. историю с labels.json) в проекте
  уже были проблемы. Если появится переиспользуемая логика записи,
  не привязанная к конкретному cv2-скрипту, — тогда и заводить
  src/recorder.py, не раньше.

## Сигнатуры модулей (см. functional requirements)

landmarks.py
  class HandTracker:
      def detect(frame_bgr, timestamp_ms) -> list[HandResult]

features.py
  def frame_to_vector(hands: list[HandResult]) -> np.ndarray   # (128,)
  def normalize_window(window: np.ndarray) -> np.ndarray       # (60,128)->(60,128)

dataset.py
  def load_labels(labels_csv_path=None) -> dict[str, dict]   # реализовано
  def record_sample(label, window, person, session, *,
                    lighting="", background="",
                    distance_m=None, notes="") -> None       # реализовано
  def load_dataset(data_dir=None) -> tuple[np.ndarray, np.ndarray, np.ndarray]
                                                             # реализовано; X, y, groups
  def split_by_group(X, y, groups, val_groups) -> tuple
      # реализовано; -> (X_train, y_train, X_val, y_val), без groups на
      # выходе. ValueError, если датасет пуст, или после разбиения train
      # или val пустой (типично — опечатка в val_groups при малом числе
      # сессий), с явным указанием, что произошло и какие группы есть.
  def augment(window: np.ndarray, seed: int | None, *,
              add_noise=True, add_shift=True, add_scale=True) -> np.ndarray
      # реализовано. Применяется к СЫРОМУ окну (до normalize_window).
      # Три независимых преобразования с отдельными флагами: гауссов шум
      # на координатах, один сдвиг на всё окно, один множитель масштаба
      # на всё окно (не по кадрам — иначе портится траектория/дрожит рука).
      # Не трогает флаги видимости и координаты отсутствующей руки (флаг=0).
      # seed=None -> недетерминированно, seed=int -> воспроизводимо (NFR-4).

predictor.py
  class RealtimePredictor:
      def push(vector: np.ndarray) -> None
      def result() -> tuple[str | None, float, list[tuple[str, float]]]

Не меняй эти сигнатуры без явного запроса — на них завязаны другие модули.

## Как работать над кодом

1. Один модуль — одна задача. Не пиши сразу несколько файлов из src/,
   если явно не попросили.
2. Перед кодом — сначала план в 3–5 пунктов, что собираешься делать.
   Дай мне подтвердить, потом пиши код.
3. Каждый модуль сопровождается тестом в tests/ на его ключевую логику
   (особенно: порядок рук, нормализация, длина окна, разбиение по группам,
   сглаживание предсказаний).
   Тесты, которым нужен файл модели models/hand_landmarker.task (он не
   хранится в git), помечаются pytest.mark.skipif с понятной причиной —
   пропускаются, а не падают. Отсутствие скачанного файла не должно
   выглядеть как сломанный код.
   Тесты, которые пишут на диск, работают только во временной папке
   (tmp_path + monkeypatch путей config.*) и никогда не трогают
   настоящие data/ проекта.
4. Комментарии и docstring — на русском. Я учусь, мне важно понимать код,
   а не просто получить рабочий результат.
5. После любого готового модуля — короткое объяснение простыми словами:
   что делает файл, почему тут именно такое решение.
6. Не добавляй зависимости, которых нет в requirements.txt, без вопроса.
7. Не трогай уже принятые и закоммиченные модули без явной просьбы.

## Что вне рамок проекта — не предлагать

Распознавание фраз/грамматики, мимика, дактиль, веб/мобильная версия,
несколько человек в кадре одновременно, облачные сервисы и базы данных.
Если кажется, что задаче не хватает одного из этого — сначала спроси,
а не добавляй сам.
